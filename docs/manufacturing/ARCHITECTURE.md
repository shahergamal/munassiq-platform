# وحدة التصنيع: قرار البنية وخطة المراحل

مبني على `00-discovery.md`. لا كود إنتاجي في هذه المرحلة. البنود المعلّمة **[قرار]** تنتظر الموافقة.

## 1. أين تعيش الوحدة
**نواة مشتركة + طبقة قطاع**، داخل نفس الـ Monolith ونفس القاعدة:

```
apps/api/src/routes/
  restaurants/*        ← القائم (يبقى كما هو)
  core/*               ← جديد: ما يخدم كل القطاعات (الفترات المالية، مراكز التكلفة، الموارد البشرية والرواتب، المهام)
  manufacturing/*      ← جديد: مراكز العمل، المسارات، BOM، أوامر التشغيل، MRP، الجودة، الصيانة، التكاليف
apps/api/src/lib/manufacturing/  ← منطق نقي مختبر بالوحدات (تفجير BOM، التكلفة، الوحدات المعادلة، MRP، الجدولة)
apps/web/src/routes/manufacturing/*
```

- **الصنف:** يُعاد استخدام جدول `ingredients` كجدول الأصناف العام (بإضافة `item_type` و`name_en` و`sale_price` و`tax_category`… في migration جديدة)، لأن المخزون والدفعات والباركود والاستلام والتحويل والجرد والهدر كلها مبنية عليه ومختبرة. في واجهة التصنيع يُعرض باسم «الأصناف». إعادة تسمية الجدول ستكسر ~200 مسار واختبار بلا فائدة للمستخدم. **[قرار 1]**
- **حسابات منفصلة للمخزون:** كل صنف يُحدَّد حسابه من نوعه (خام 1106-1، تحت التشغيل، تام، قطع غيار) بدل حساب المخزون الواحد. المطاعم تبقى على حسابها الحالي.

## 2. التقييد بالقطاع (ضروري قبل التفعيل)
- `tenants.sector` يصبح مقروءاً في `requireTenant`: كل مسار يعلن قطاعاته (`sectors: ["manufacturing"]`)، والنواة لكل القطاعات. منشأة مطعم تستدعي مسار تصنيع ← 404.
- `NAV` في الويب يُرشَّح بالقطاع ثم بالصلاحية، وكذلك الـ Guard في الراوتر، و`CATALOG` يُعرض في محرر الأدوار حسب القطاع (مصنع لا يرى «الصالات والطاولات» ولا «شاشة المطبخ»).
- الزرع حسب القطاع: دليل حسابات تصنيع، وحدات قياس صناعية، تصنيفات مصروفات مصنع، أدوار جاهزة (مخطط إنتاج، جودة، موارد بشرية…).
- باقات `manufacturing-trial/starter/pro` في `plans`. **[قرار 5]**
- `sectors.is_available = true` يحدث **في آخر migration لأول مرحلة تصنيع مكتملة ومختبرة**، التزاماً بالقاعدة «لا قطاع يُباع قبل تنفيذه».

## 3. العزل بين المستأجرين
كما هو: `tenant_id` في كل جدول، RLS بـ `current_tenant_id()` و`tenant_is_operational()` للكتابة، `withTenantTx`، فهارس تبدأ بـ `tenant_id`. يُضاف لكل migration اختبار في `isolation.test.ts` بأن منشأة لا ترى صفوف أخرى في الجداول الجديدة.

## 4. نموذج البيانات المختصر (المرحلة 4)
| جدول | الأهم فيه |
|---|---|
| `work_centers` | سعة يومية، ساعات تشغيل، تكلفة ساعة آلة/عمالة/أعباء، موقع الإنتاج |
| `routings` / `routing_operations` | تسلسل، مركز عمل، زمن إعداد وتشغيل لكل وحدة، مقاولة خارجية |
| `boms` / `bom_lines` / `bom_byproducts` | صنف ناتج، إصدار، سريان من/إلى، كمية أساس؛ مكوّن، كمية، هالك متوقع %، بديل، Phantom؛ منتج ثانوي بنسبة توزيع تكلفة |
| `manufacturing_orders` | الحالات draft → confirmed → reserved → in_progress → done → closed، BOM ومسار مجمّدان عند التأكيد |
| `mo_issues` / `mo_outputs` / `mo_labor` / `mo_scrap` | صرف فعلي بالدفعة، ناتج جزئي ودفعته، أزمنة فعلية، هالك عادي/غير عادي — كلها إضافة فقط |
| `cost_rollups` | تكلفة معيارية مجمّدة لكل إصدار BOM لحساب الانحرافات |
| `mrp_runs` / `mrp_suggestions` | لقطة التشغيل ونتائجها (أوامر شراء/تشغيل مقترحة) |
| `qc_plans` / `qc_inspections` / `ncrs` | الفحص بالدفعة، حجز/إفراج بموقع حجر، عدم مطابقة |
| `machines` / `maintenance_plans` / `maintenance_orders` / `downtimes` | الصيانة الوقائية وأثرها على السعة |

**القيود (دوال جديدة في `posting.ts` + `SOURCES`):** صرف (مدين تحت التشغيل / دائن خام)، تحميل عمالة وأعباء (مدين تحت التشغيل / دائن أعباء محمّلة)، ناتج (مدين تام / دائن تحت التشغيل)، هالك غير عادي (مدين مصروف هالك)، انحرافات عند الإقفال، تسوية الأعباء نهاية الفترة. **شرط القبول:** إقفال الأمر يُصفّر رصيده في تحت التشغيل.

## 5. طريقة التكلفة **[قرار 3]**
- المتاح اليوم: متوسط مرجّح متحرك لكل موقع، وهو مقبول في IFRS (IAS 2).
- التوصية: **المتوسط المرجّح + تكلفة أوامر (Job) فعلية** أولاً، ثم **المعيارية بالانحرافات** كخيار للمنشأة. FIFO بطبقات تكلفة يحتاج إعادة كتابة `takeOut`/`putIn` لكل العمليات القائمة، فيُؤجَّل لمرحلة مستقلة إن طلبه عميل فعلي. تكلفة المراحل (Process بالوحدات المعادلة) تأتي بعد المعيارية.

## 6. التكامل مع القطاعات الأخرى
- **المشترك:** المحاسبة، زاتكا، الموردون، الفروع، المواقع، الوحدات، المشتريات، المخزون والدفعات، الموارد البشرية والرواتب (جديدة في النواة؛ تفيد المطاعم مباشرة).
- **خاص بالمطاعم ويُخفى عن المصانع:** الكاشير، الطاولات، الإضافات، شاشة المطبخ، تطبيقات التوصيل، وصفات المنيو.
- **المبيعات:** يُبنى لكل القطاعات: عرض سعر ← أمر بيع بحجز ← إذن تسليم (يُخرج المخزون ويقيد تكلفة المبيعات) ← الفاتورة الضريبية القائمة (زاتكا جاهز).

## 7. خطة المراحل المقترحة (معدّلة لما هو موجود فعلاً)
الملف يوصي بترتيب 0←1←2←3←5 ثم 4. لكن 1 و5 منفّذتان بدرجة كبيرة للمطاعم، والفجوة الحقيقية هي التصنيع نفسه. الترتيب المقترح **[قرار 2]**:

| # | المحتوى | المخرج القابل للبيع |
|---|---|---|
| M1 | التقييد بالقطاع + الزرع (دليل حسابات تصنيع، وحدات، أدوار) + نوع الصنف وحساباته + مراكز التكلفة + السنوات والفترات المالية | منشأة تصنيع تُنشأ وتعمل على المشتريات والمخزون والمحاسبة الحالية |
| M2 | مراكز العمل، المسارات، BOM متعدد المستويات بإصدارات، Cost Roll-up، أوامر التشغيل بحالاتها وقيودها وWIP والهالك والمنتج الثانوي | **يُفعَّل القطاع هنا** |
| M3 | المبيعات للتصنيع: عملاء B2B، عرض، أمر بيع بحجز، تسليم بتكلفة مبيعات، دفعة مقدمة 386، مطابقة فاتورة المورد الثلاثية، الاستقطاع، توزيع التكلفة الواصلة بالوزن/الكمية | دورة P2P وO2C كاملة |
| M4 | MRP + الجدولة بسعة محدودة (Gantt) + التكلفة المعيارية بالانحرافات + تسوية الأعباء | تخطيط الإنتاج |
| M5 | الجودة والتتبع الأمامي والخلفي + الصيانة الوقائية | |
| M6 | زاتكا: جهاز لكل فرع، 386 وأعلام KSA-2، عامل إبلاغ دائم، SDK الهيئة في CI، التحقق الحي على بيئة المطورين | |
| M7 | الموارد البشرية والرواتب (نواة): موظفون، عقود، حضور، إجازات، مسير، GOSI بجدول سريان، نهاية الخدمة م84/85/87، ملف مُدد وملفات البنوك، تشفير الحقول الحساسة | |
| M8 | التقارير (إنتاج، تكاليف، OEE، رواتب) + التصليب (CI، MFA، Playwright، اختبار حمل) | منفذة (راجع HANDOFF) |

كل مرحلة: migration ← منطق نقي باختبارات وحدة ← API باختبارات تكامل ← الشاشات ← توثيق في HANDOFF، ولا انتقال قبل نجاح الاختبارات.

## 8. المخاطر والأسئلة المفتوحة
1. **اللغة الإنجليزية/LTR [قرار 4]:** الواجهة عربية بالكامل بنصوص مكتوبة داخل المكونات. إضافة الإنجليزية = استخراج آلاف النصوص إلى قاموس وتحويل CSS لخصائص منطقية. التوصية: الأسماء الإنجليزية للأصناف والمنشأة والحقول في المستندات الآن (تحتاجها الفواتير)، وترجمة الواجهة كمرحلة مستقلة لاحقاً.
2. **التاريخ الهجري:** عرض مزدوج (أم القرى عبر `Intl` بتقويم `islamic-umalqura`) في المستندات والتقارير — بلا مكتبة، منخفض المخاطر، يُضاف في M1.
3. **حجم العمل:** التصنيع العميق (M2-M5) + الرواتب (M7) أكبر من كل ما بُني حتى الآن. كل مرحلة تُسلَّم وتُختبر منفصلة.
4. **زاتكا الحي:** لم يُختبر على بوابة الهيئة (تعذّر DNS سابقاً). يلزم تشغيل فعلي على بيئة المطورين قبل البيع لمصنع.
5. **الأرقام التنظيمية من مصادر ثانوية** (الغرامات، عدد فحوصات الامتثال، صيغ ملفات البنوك): تُبنى إعدادات لا ثوابت.
6. **الاستضافة داخل المملكة (PDPL):** قرار تشغيلي خارج الكود، مذكور في `docs/DEPLOY_AR.md` لاحقاً.

## 9. قائمة القرارات المنتظرة
1. إعادة استخدام جدول الأصناف الحالي (موصى به) أم جدول أصناف جديد للتصنيع.
2. ترتيب المراحل M1←M8 أعلاه (موصى به) أم ترتيب الملف الحرفي.
3. طريقة التكلفة الأولى: متوسط مرجّح + أوامر فعلية ثم معيارية (موصى به)، أم FIFO من البداية.
4. الإنجليزية: حقول ثنائية اللغة في البيانات والمستندات الآن وترجمة الواجهة لاحقاً (موصى به)، أم ترجمة كاملة الآن.
5. أسعار باقات التصنيع وحدودها (فروع/مستخدمون).
